# Codex Review - 2026-05-05

## Executive Summary

This branch removes several high-impact gaps in the compose-to-Apple-Container path and tightens a few security-sensitive filesystem behaviors. The main value is not a broad refactor, but a set of focused fixes that reduce silent drift between commands, make `pull --include-deps` behave correctly, preserve top-level `models`, and harden temp-file handling for configs and secrets.

## Findings

### 1. Unsupported build flags drifted across `build`, `up`, and `create`

**Files:** `Sources/Container-Compose/Commands/ComposeBuild.swift`, `Sources/Container-Compose/Commands/ComposeUp.swift`, `Sources/Container-Compose/Commands/ComposeCreate.swift`

**Finding:** The command paths were not aligned. `ComposeBuild` already warned and skipped unsupported `build.network`, `build.shm_size`, `build.ssh`, `build.cache_from`, `build.cache_to`, and `build.entitlements`, but `ComposeUp` and `ComposeCreate` still emitted some unsupported build flags. That created inconsistent behavior for the same compose file depending on command.

**Recommendation:** Keep the warning policy centralized and shared across every command that consumes `Build`. Do not let build-arg emission logic drift back into per-command code.

**Status:** Fixed in this branch by centralizing the warnings in `Compose+BuildWarnings.swift` and removing unsupported flag emission from `up` and `create`.

### 2. `pull --include-deps` was not selecting dependencies reliably

**File:** `Sources/Container-Compose/Commands/ComposePull.swift`

**Finding:** The dependency selection logic depends on `dependedBy`, but `ComposePull` was filtering services before the graph had been topologically sorted. In practice that meant `--include-deps` could miss services that should have been pulled first.

**Recommendation:** Any command that uses reverse dependency traversal should normalize the service graph first, before selecting target services.

**Status:** Fixed in this branch by topo-sorting after profile filtering.

### 3. Top-level `models` were decoded but not preserved on round-trip

**File:** `Sources/Container-Compose/Codable Structs/DockerCompose.swift`

**Finding:** `DockerCompose` decoded `models`, but `encode(to:)` and `loadComposeDocument` dropped the field. That meant a loaded or merged document could silently lose a top-level compose feature even when the parser accepted it.

**Recommendation:** Every decoded top-level field should survive encode/load unless there is an explicit compatibility reason to strip it. If a field is intentionally dropped, document that in the type or parser.

**Status:** Fixed in this branch by encoding and carrying `models` through document loading.

### 4. Config and secret temp materialization used weak path hygiene

**File:** `Sources/Container-Compose/Commands/Compose+ConfigsAndSecrets.swift`

**Finding:** The temp directory and file names were built directly from project/source names. That made path components noisier than necessary and left the materialized config/secret files with weaker filesystem hygiene than they should have had.

**Recommendation:** Sanitize all host-side path components before building temp paths, and set explicit permissions for directories and files that contain config or secret material.

**Status:** Fixed in this branch by sanitizing path components and setting `0700` on the directory and `0600` on materialized files.

### 5. `shm_size` and stop settings still emitted unsupported runtime flags

**Files:** `Sources/Container-Compose/Commands/Compose+ArgsResource.swift`, `Sources/Container-Compose/Commands/ComposeRun.swift`

**Finding:** `service.shm_size`, `service.stop_signal`, and `service.stop_grace_period` were still being translated into unsupported Apple Container argv. That is the kind of feature mismatch that causes runtime surprises instead of clean warnings.

**Recommendation:** Prefer warn-and-skip over argv emission whenever the upstream runtime does not support a compose field. Keep the user-facing warning text consistent across code paths.

**Status:** Fixed in this branch.

## Recommendations

### High Priority

1. Keep the unsupported-field policy centralized. The branch already moved in this direction; do not reintroduce one-off warning logic in future command implementations.
2. Treat `ComposePull` and any future graph-sensitive command as graph-first code. Normalize the service graph before selecting targets.
3. Preserve every top-level compose field that the parser accepts unless the codebase has a deliberate compatibility reason not to.

### Medium Priority

4. Extract more of the remaining `ComposeUp` filesystem logic into helpers if more temp-file or volume handling work lands. The current branch improved config/secret handling, but similar path construction issues can still appear elsewhere.
5. Continue replacing silent feature drift with explicit warnings for any compose field that Apple Container does not support yet.
6. Review runtime command lookup and other PATH-based execution points for whether they should be narrowed or made explicit.

### Lower Priority

7. Keep the review docs current when new feature gaps are found. The branch closed several gaps, but the repo still benefits from a running list of unsupported compose features and the command paths they affect.
8. If `label_file`, IPAM subnet/gateway wiring, or other partially supported fields are revisited, cover them with tests before changing the runtime path.
